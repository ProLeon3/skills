## 1. 确定需求基准

- **ticket**：功能轴以它的「验收标准」为准。再顺着「来源」读 spec，但只取 Implementation Decisions、Testing Decisions、Out of Scope 作为约束。
- **spec**：以 Acceptance Criteria 为准，并用 User Stories 补充正常路径、边界情况和错误路径。
- **用户描述**：先整理成可以逐条判定的验收条目，并写进报告。
- 三者都没有：功能轴标为"未检查"，只审可维护性，不要臆造需求。

## 2. 收集改动

```bash
git status --short
git diff HEAD                              # 已暂存和未暂存改动合在一起的结果
git ls-files --others --exclude-standard   # 未跟踪文件：逐个读全文，不能只看文件名
```

用户指定了范围时，以用户指定的为准。没有任何改动时，告知用户后结束。

不能只看 diff。还要沿调用链读改动涉及的调用方和被调用方，才能判断最终行为，以及对既有功能的影响。

## 3. 功能轴

对每个验收条目给出判定：**满足 / 部分满足 / 未满足 / 无法判定**，并附上证据（`文件:行号`、测试名或命令输出）。

- 能运行的检查就运行：相关测试、构建和 lint 的结果都是证据，失败本身就是发现。读代码和跑测试都无法确认的条目，标为"无法判定"，并写明需要怎样手动验证。
- 逐条对账之外，还要找：边界和错误路径上的缺陷、对既有行为的回归、需求之外的额外行为、与 Implementation Decisions 不一致的实现。
- 实现如果替 spec 的 Open Questions 做了选择，把它列进"需用户确认"，不算缺陷。

## 4. 可维护性轴

以仓库自身的标准为准：CLAUDE.md、AGENTS.md 等规范文件，lint 配置，以及相邻代码的惯例。只审本次改动引入或加重的问题，原本就存在的问题不报。

重点看：

- **位置与边界**：逻辑是否落在 spec、ticket 约定的模块和接口里；有没有绕开既有分层，或把职责塞进无关的模块。
- **复用**：新写的逻辑在仓库里是否已有等价实现。先搜索，再下结论。
- **测试**：是否覆盖验收条目对应的外部行为；是否落在 spec Testing Decisions 约定的切入点，并参照了其中的先例；是否绑定了实现细节。
- **注释**：中文注释是否解释了不明显的规则、约束和原因，并且与代码一致。只是复述代码的注释算噪音。

## 5. 报告

- **必须修复**：验收条目未满足或部分满足、功能缺陷、回归失败、违反 spec 已做的决策。
- **建议**：可维护性上的判断题；证据不足的疑点也放在这里，并注明证据不足。

按照以下格式撰写最终报告，文件保存到对应的 spec文件 或 ticket文件 相同目录下，文件命名为 `{name}-review_result.md`，name 指代 spec或ticket 文件名。 

```markdown
## 结论
<通过 / 需修改：N 条必须修复，M 条建议>

## 功能性
| 验收条目 | 判定 | 证据 |
|---|---|---|

## 可维护性
<发现列表>

## 需用户确认
<对 Open Questions 自行做出的选择、无法判定的条目。没有就删掉本节>
```

没有发现问题就如实写没有，不要为了显得认真而凑数。

最后告知用户"**review-implement 已完成**"。
