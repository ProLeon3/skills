# 平实写作规则

规则分为三组：用词与语气、句子与段落、要避免的模式。多数规则附有改前和改后的示例。

## 用词与语气

1. **用简单的日常用词。** 平实的词够用时，不要挑花哨的同义词。也要避免 AI 工具滥用的词，例如英文的 "delve"、"robust"、"leverage"，中文的"赋能"、"重塑"、"深度剖析"。
  改前: 我们利用缓存赋能更健壮的查询体验。
  改后: 我们用缓存让重复查询更快。

2. **不用行话。** 始终使用人能听懂的语言，就像两个人平常交谈那样。不要发明行话或缩略说法，词典里查不到的词或短语就不要用。只有当既有技术术语最精确时才使用它，并在读者可能不了解时简要解释。
  改前: 这个分数是该性质是否成立的一个经过校准的代理指标。
  改后: 这个分数估计该性质成立的可能性有多大。

3. **术语保持一致，控制用词范围。** 同一个东西全程用同一个词称呼。例如：不要在"文档"、"文件"、"记录"之间来回换。

4. **让文字保持朴素、描述性和解释性。** 不要使用吸引眼球的短语、口号、巧妙的标签，或刻意让人记住的措辞。本条规则适用于所有地方：标题、主题句、提示框、标签、总结和普通正文。
  改前: 通过全链路闭环拉通，我们将彻底激活底层生产力潜能。
  改后: 完成上述工具配置后，工程师每日构建代码的等待时间预计减少 40%。

## 句子与段落

1. **写完整的句子。** 每个句子都要有主语和谓语。不要写残缺的片段，也不要用冒号或分号把不相关的意思拼在一起。
  改前: 用于过滤无效请求。如果超时。
  改后: 该中间件用于过滤无效请求。如果客户端请求超时，网关会直接返回 504 错误。

2. **介绍工作流程或先后顺序时，按顺序逐步讲。** 用"第一""第二""第三"引导，每一步单独成句，让读者能跟上，也可以用分号分隔各步。
  改前: 特征的分组来自作者自己的阅读，示例帖子是手写的，更细的粒度则意味着再训练几个小模型并重新标注。
  改后: 第一，作者根据自己对输出的阅读，亲自把特征分成了几组。第二，示例帖子由他们手工撰写。第三，需要更细的粒度时，他们再训练一个小模型，并重新标注帖子。

3. **段落按主题句加支撑来组织。** 每个段落或小节以陈述要点的主题句开头。接下来一句给出支撑性的例子或事实，必要时再补一句说明。之后用"比如""另外""或者"这类普通连接词引出更多支撑。
  改前: 解析器会跳过没有变化的文件。缓存保存着上一次的输出。大多数渲染都很快。
  改后: 大多数渲染都很快。比如，解析器会跳过没有变化的文件，服务器直接提前返回。另外，缓存保存着上一次的输出，重复渲染不用做任何工作。

4. **偏向长的解释性句子，而不是短促有力的句子。** 普通正文里，像人们口头解释事情那样写，句子长一些，带着逗号，把要点用最简单的方式说清。不要把一个想法拆成一堆短句，也不要写朗朗上口的短语。只有在带标签的简报、要点列表或"第一/第二/第三"顺序里，短句才合适。
  改前: 门禁在每次合并时运行。它拦截回归。没人绕得过去。
  改后: 门禁在每次合并时运行，会拦截回归用例失败的变更。除非有人刻意跳过检查，回归不会进入生产环境。

5. **在对话中交代问题背景。** 来回聊天时，要写给一位聪明但不了解问题背景、或者已经忘了背景的读者看。先交代问题背景和之前发生的事，再说明这次改了什么。铺垫要精简，不要倒出全部历史。写文章时忽略本条规则。
  改前: 导出器现在会等 reset 头了，`dotnet test` 全绿。
  改后: Okta System Log 导出器之前会重读整小时的数据，重试可能把同一个事件写两次，现在它按响应里的 reset 头等待。六个验收测试全部通过。

## 要避免的模式

1. **不要赋予无生命的东西虚假的能动性。** 当真正的执行者是人或流程时，不要把系统或物体写成会自行转变、决定或打算做什么。对工具和系统使用普通的事实性动词是可以的，例如"API 返回 JSON""任务把文件写入磁盘"。以人或流程作主语更清楚时，优先这样写。
  改前: 任务跑完后，日志就变成了可检索的记录。
  改后: 任务跑完后，你就可以检索日志。

2. **不要使用指代不明的指示代词。** 不要用"这""那""这些""那些"做指代不明的指代。尤其不要用指示代词开头一个句子，段落的第一句更是任何位置都不要出现指示代词。
  改前: 这会延续到下一轮。
  改后: agent 会在下一轮应用你保存的规则。
