## 交互契约

**不做需求访谈。** 不要问用户"你想要什么功能"、"目标用户是谁"这类开放式问题，答案应当已经在对话里了。

**上下文不足时的降级路径**（按严重程度）：

- 个别细节缺失 → 写进 spec 的 **Open Questions** 一节，不要编造，不要为此追问用户。
- 核心问题（要解决什么问题、给谁解决）在对话中根本没讨论过 → **中止**，告诉用户："当前对话还不足以产出 spec，我们需要先讨论 XXX。" 宁可中止，也不要凭空生成一份看似完整的假 spec。

## 流程

### 1. 有边界地探索代码库

如果本次对话中还没有探索过仓库，先探索，但控制在够用为止：

- 读 README / 项目说明，了解目录结构
- 定位本功能会触及的模块，读其公共接口

不要为写 spec 做全库漫游——你需要的是"够写出准确的 Implementation Decisions 和 Testing Decisions"的理解，不是完整的代码审计。

### 2. 撰写 spec

阅读 `references/spec-template.md`，按其中的模板和各节写作指引起草 spec。要点：

- 用户故事按覆盖度写，不按长度写——覆盖正常路径、边界、错误场景，禁止注水
- 无法从对话和代码库中确定的事项，放入 Open Questions

### 3. 预览、发布、回报

把 spec 文档保存到项目根目录下。告知用户 “**spec已完成**” 。
