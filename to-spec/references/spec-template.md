# Spec 模板与各节写作指引

按下面的结构撰写 spec。每节先看写作指引，再落笔。

---

## Problem Statement

用户正面临的问题，**从用户的视角**描述。写清楚：谁、在什么场景下、需要什么。不写解决方案，不写技术。

## Solution

该问题的解决方案，仍然从用户的视角描述，一段简洁描述即可，技术细节留给 Implementation Decisions。

## User Stories

带编号的用户故事列表，格式：

```
1. 作为一个 <角色>，我想要 <功能>，以便 <收益>
```

示例：

> 1. 作为一名手机银行客户，我想看到我各个账户的余额，以便我能对自己的支出做出更明智的决定

**写作指引（重要）：**

- 目标是**覆盖度**，不是长度。逐一检查三类场景是否覆盖：正常路径、边界情况、错误/失败路径。覆盖到了就停笔。
- 每条故事必须对应一个可区分的用户可见行为。
- 只写对话中讨论过或可从代码库合理推出的故事；推测性的需求进 Open Questions，不进这里。

## Acceptance Criteria

可逐条验证的完成标准。每条应当能被回答"是/否"，例如"未登录用户访问余额页时被重定向到登录页"。这一节是实现方和审阅方的对账依据，避免含糊词（"体验良好"、"性能可接受"）——能量化就量化，不能量化就写成可观察的行为。

## Implementation Decisions

**已经做出**的实现决策列表（来源：对话讨论 + 代码库现状）。可包括：

- 将要构建/修改的模块，以及这些模块中将被修改的接口
- 来自开发者的技术澄清、架构决策
- Schema 变更、API 约定、具体交互方式

**不要**包含具体的文件路径或大段代码——它们过时得很快，模块和接口的名字比路径稳定。

尚未做出的决策不要在这里"顺手拍板"，放入 Open Questions。

## Testing Decisions

已经做出的测试决策列表：

- 测试将落在哪些测试切入点
- 哪些模块将被测试
- 这些测试在代码库中的**先例**（指出类似类型的既有测试，实现者照着写）
- 测试哲学：只测外部行为，不测实现细节

## Out of Scope

明确排除在本 spec 之外的事项。把讨论中提过但决定不做、或容易被误以为包含的内容写在这里，防止范围蔓延。

## Open Questions

从对话和代码库中**无法确定**、但会影响实现的事项。每条写清：问题是什么、为什么影响实现、推荐的选项。这一节是"不做访谈"策略的安全阀——有疑问写在这里，不编造答案。若本节为空，删除该节。

## Further Notes

其他补充说明。若无，删除该节。
